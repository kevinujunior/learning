## 🔑 Key Takeaways

### Most Frequently Used Design Patterns in LLD Interviews

Strategy — 26/30 problems (nearly universal)
Observer — 16/30 problems
State — 10/30 problems
Factory — 8/30 problems
Chain of Responsibility — 7/30 problems
Command — 7/30 problems
Decorator — 8/30 problems

| Pattern | Core Purpose | When to Reach for It in an Interview |
|---|---|---|
| **Strategy** | Swap algorithms / behaviors at runtime without modifying clients | Any time the problem has multiple ways to do the same thing (pricing, sorting, matching, formatting). Almost always applicable. |
| **Observer** | Decouple event producers from consumers | Any time one change should trigger reactions in multiple places (notifications, feed fanout, budget alerts, status updates). |
| **State** | Manage complex lifecycle transitions cleanly | Any entity that moves through well-defined stages: orders, trips, bookings, ATMs, elevators. Replaces giant `if-else` chains. |
| **Factory / Factory Method** | Decouple object creation from usage | When you have a family of related objects (Vehicle types, Payment providers, Sandbox runners) and the caller shouldn't know concrete classes. |
| **Singleton** | Single shared instance with global access | For stateful central managers: `ParkingLot`, `LockManager`, `Logger`, `IDGenerator`. Use sparingly — mention thread-safety concerns. |
| **Decorator** | Add responsibilities to objects without subclassing | Layering features on top of a base service (coupons, TTL on cache, analytics on redirect, room add-ons). |
| **Chain of Responsibility** | Pass requests through a dynamic handler chain | Multi-step validation (payment, coupon, log routing). Order matters; each handler decides to handle or forward. |
| **Command** | Encapsulate a request as an object | Needed for undo/redo (chess, cart), queuing (task scheduler, judge), or auditability (banking, file operations). |
| **Composite** | Treat individual objects and compositions uniformly | Tree structures: file systems, menus, organizational hierarchies. |
| **Template Method** | Define the skeleton of an algorithm; subclasses fill in steps | Fixed workflows with variable steps: report generation, payment flow, game loop. |

### Common Mistakes Candidates Make in LLD Interviews

1. **Jumping to code without clarifying requirements** — Always spend 2–3 minutes asking about scale, actors, and constraints before drawing a single class.

2. **Overusing Singleton** — Many candidates apply Singleton everywhere as a default. Justify it explicitly; always mention thread-safety (`double-checked locking`, `enum Singleton`).

3. **Naming patterns without justifying them** — Saying "I'll use Strategy" without explaining *why* it fits this specific problem is a red flag. Always explain the problem it solves here.

4. **Flat class hierarchies with no interfaces** — Interviewers expect programming to interfaces. Every behavioral boundary should be an interface or abstract class.

5. **Ignoring concurrency** — For shared resources (parking spots, seats, KV store), mention locks, `synchronized` blocks, `ConcurrentHashMap`, or optimistic locking. Forgetting this is a major gap.

6. **Conflating Observer with Pub-Sub** — Observer is in-process, tightly coupled to the subject. Pub-Sub uses a broker and is fully decoupled. Know the distinction.

7. **Over-engineering simple problems** — Applying 5 patterns to an LRU Cache signals poor judgment. Sometimes the right answer is a custom data structure, not a GoF pattern.

8. **Skipping enumerations for status fields** — Use `enum` for states, roles, and categories. Strings are error-prone and lose type safety.

9. **No separation of concerns** — Business logic inside entity classes (`Order.calculateTax()`) is a smell. Push computation to services; keep entities as data holders.

10. **Not defining extension points** — Always mention where the design is open for extension (new vehicle types, new payment providers) without modification — this demonstrates OCP awareness.
